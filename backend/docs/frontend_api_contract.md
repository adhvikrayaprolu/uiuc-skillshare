# Browser API contract

Django authorizes verified eligible members. Use same-origin requests with cookies (`credentials: include`); unsafe methods also send `X-CSRFToken` from the current `csrftoken` cookie. Never store access tokens in localStorage. Domain schemas are at `/api/schema/` and `/api/docs/`; the allauth-based authentication endpoints below are documented separately.

## Authentication

| Endpoint | Behavior |
|---|---|
| GET `/api/auth/csrf/` | CSRF bootstrap plus `googleEnabled`, `demoEnabled` and `authenticated` (whether a session cookie exists, so signed-out clients skip `/me/`). Obtain before unsafe requests and again after login. |
| POST `/api/auth/demo/` | Local development only (`DEMO_MODE=true`, refused outside `ENVIRONMENT=local`; otherwise 404). CSRF required. Signs in to the seeded demo member, or the demo moderator with `?account=staff`; returns `{user}`. 503 when the demo network is not seeded. |
| POST `/api/auth/email/request/` | `{email}` with exact Illinois domain; returns allauth 401/code-required response without authenticating. Local codes arrive in Mailpit. |
| POST `/api/auth/email/confirm/` | `{code}`; success 200 creates a server-controlled session. Five-minute expiry, three failed attempts; replay/stale process fails. |
| POST `/api/auth/email/resend/` | Throttled resend within the active verification process. |
| POST `/api/auth/google/` | `{provider:"google", process:"login", token:{client_id, id_token}}`; configured audience and authoritative Illinois ownership required. Non-authoritative ownership falls back to an email code. |
| GET / PATCH `/api/auth/me/` | Current member and editable account preferences; session restoration uses GET. Read-only `is_staff` lets the client hide staff-only navigation; the server still enforces staff permissions. |
| POST `/api/auth/logout/` | Deletes server session; client clears account-specific query/cache state. |
| GET `/api/auth/export/` | Own account data download, no-store. |
| POST `/api/auth/delete/` | `{confirmation:"<own account email>"}`; confirmed deletion/session revocation and durable avatar cleanup. |

Allauth validation errors use `{status, errors:[{message,...}]}`; domain APIs use DRF field/detail errors. Suspended/inactive users and legacy `is_demo` records cannot authenticate. JWT refresh routes are absent, and the demo sign-in route exists only in local development. A 401 domain response expires frontend session state; refresh cannot resurrect it.

## Profiles / taxonomy

GET `/api/bootstrap/` supplies current user/profile, approved categories/skills and dashboard tasks; GET `/api/onboarding/status/` supplies `has_completed_onboarding` and `missing_steps` (any of `create_profile`, `add_basics`, `add_skills`, `add_learning_goals`, `add_availability`). Setup is complete only with display name, major, year, headline, at least one teaching skill, at least one learning goal, and availability (a slot or availability notes); bio is optional. The server recomputes the flag on every profile save. PUT `/api/profiles/me/aggregate/` atomically saves `{profile, skills?, availability?, contacts?, credentials?}`. Omitted relation lists are preserved; supplied lists replace that relation. Field errors roll back the entire save. Profile fields include learning goals, contact/embedding/email consent and visibility; evidence uses HTTP/HTTPS links. POST `/api/profiles/me/avatar/` uses multipart `avatar` (up to 2 MB, 4096px input); GET `/api/profiles/<id>/avatar/` enforces peer privacy.

`learning_goals_public` (default `false`) controls whether a member's approved learning goals appear on their profile detail as `wants_to_learn` (`[{id, name}]`); notes are never exposed. Profile detail also returns a viewer-specific `swap` (`{they_teach_you, you_can_teach, is_mutual}`, or `null` on your own profile). `you_can_teach` is empty unless the member's goals are public.

GET `/api/discovery/swaps/` returns paginated two-way matches: open, visible members who teach one of your goals and publicly want to learn one of your skills. Each result has `swap` and `match_reasons`; results are ordered by overlap, then shared availability slots. `matching` is `{basis: "swap", reason}`, where `reason` is `no_profile`, `no_learning_goals`, `no_teaching_skills`, `no_mutual_matches` or `null`.

GET `/api/profiles/` and `/api/profiles/<id>/` show visible peers only. Selected contact methods appear only after accepted/completed interaction and sharing consent; block/privacy/removal revokes access. Authentication emails and private goals never appear in public serializers. GET `/api/skills/` and `/api/skill-categories/` supply the approved taxonomy and are readable without signing in (pending suggestions are staff-only); GET `/api/skills/popular/` requires a member session; POST `/api/skills/suggest/` creates a pending suggestion for staff approval.

## Discovery and pagination

GET `/api/discovery/search/` accepts `q`, `mode`, taxonomy `skills`/`category`, `availability_day`/`availability_time`, `open_to_connect` and explicit background filters. GET `/api/discovery/recommended/` uses private learning goals or clearly labeled discovery suggestions. Responses retain `{count,next,previous,results,matching}`. Matching metadata reports actual mode, fallback reason, candidate limit/truncation and recommendation basis. Reasons come from facts; match scores are internal ordering values, not probabilities. [Matching design](../../docs/matching.md) specifies weights and semantic gates.

Follow pagination for discovery, saved profiles, requests, notifications and taxonomy. Discovery pages are server-backed; finite personal lists retain all server pages and the UI pages them in groups of 20. A candidate cap bounds ranking and is disclosed; it is not the entire campus count.

## Requests / feedback

POST `/api/help-requests/` accepts helper profile, `related_skill` (one of the helper's skills), topic/message, urgency/preferred contact and a UUID `idempotency_key`; new status is always pending. `kind` is `help` (default) or `swap`. A swap requires `related_skill` and an `offered_skill` that is one of the sender's own approved skills and differs from `related_skill`; a help request must not send `offered_skill`. Responses include `kind`, `offered_skill` and `offered_skill_name`, and the receiver's notification is titled "New swap proposal". GET lists/retrieves participant history; every row includes `my_role` (`seeker` or `helper`) and `cancel_reason`. GET `/api/help-requests/?bucket=` filters the inbox on the server: `needs_action` is pending requests you received plus completed requests where you still owe feedback, `active` is pending requests you sent plus accepted ones, and `past` is everything else that is finished. Any other bucket returns 400. PATCH `/<id>/` accepts the next `status`, current `version`, an optional `response_message` (receiver only) and an optional `cancel_reason` (only when cancelling, max 300 characters); stale conflicts return 409. Participants/content cannot be reassigned. The receiver accepts/declines; only the sender can withdraw a pending request; either participant can cancel or complete an accepted one. Identical retries are idempotent and do not duplicate notifications.

Pending requests expire. Every row includes read-only `expires_at`, which is 14 days after creation, and `expired_at`. Seven days in, the receiver gets one reminder notification titled "A swap proposal is waiting for your reply" or "A request is waiting for your reply". At `expires_at` the background dispatcher sets status `expired`, bumps `version` and notifies both sides. `expired` is terminal and appears in the `past` bucket. PATCHing an expired request, or accepting one past its `expires_at` before the dispatcher runs, returns 400 with "This request expired without a reply…". A sender may have at most 5 pending requests. POST returns 400 with "You already have 5 requests waiting for a reply…" until one is answered, withdrawn or expires.

Retrieve and PATCH responses also include `feedback` for the current viewer (`null` in list responses): `{target_profile_id, skill: {id, name} | null, can_review, can_endorse, my_review: {rating, comment} | null, endorsed}`. The seeker gives feedback to the helper about `related_skill`; on a swap, the helper also gives feedback to the seeker about `offered_skill`. The helper of a plain help request has no feedback to give.

POST `/api/profiles/<id>/reviews/` and `/endorsements/` require a completed `help_request` in which the profile is your feedback target (see above). Each participant can leave one review and one endorsement per request, and the endorsed skill must be the one that member taught you. Feedback confirms an interaction, not independent expertise. Saved profiles use `/api/saved-profiles/`; blocked/private entries are suppressed. POST `/api/blocked-users/`, DELETE `/<id>/` and POST `/api/reports/` back the corresponding Settings/profile controls. Blocking cancels active requests and scrubs their contact/message data. The profile page confirms a block in an in-app alert dialog before posting. POST `/api/reports/` requires one target (`reported_profile`, `reported_user` or `reported_review`), a `reason` from `harassment`, `inappropriate_content`, `spam`, `fake_profile`, `misleading_credentials` or `other`, and a `description` of 10 to 2000 characters after trimming. You cannot report yourself or your own content. Reports start `open`. Staff resolve them in Django admin as `reviewed`, `dismissed` or `action_taken`, and suspending the member also counts as `action_taken`. Every action is recorded in `ModerationAudit`. Reports are never shown to members.

Policy pages `/guidelines`, `/privacy` and `/terms` are public frontend routes. Signed-in members can open them too, and they need no API.

## Notifications and statistics

GET `/api/notifications/` includes paginated results plus `unread_count`; POST `/<id>/read/` and `/read-all/` persist read state. Transactional domain events create notifications; optional email retries independently. GET `/api/dashboard/` and `/api/analytics/summary/` respect peer visibility in personal counts. Each notification's `href` is `/requests/<id>` for request events, or `/profiles/<id>` for `kind: "skill_alert"`. Notification emails link to the same page and are sent as branded HTML with a plain-text part.

Skill alerts: once a profile is first live (published, open to connect, setup complete), the dispatcher sends a `skill_alert` notification, titled "{first name} just joined and teaches {skill}", to up to 200 members who want to learn one of its skills. Recipients must have `skill_alerts_enabled` (default `true`), be eligible, and not be blocked by or blocking the new member. A profile is only announced once, so unpublishing and republishing never re-alerts. Profiles that existed before this feature are marked as already announced. Alerts disappear from the list if the teacher's profile stops being public. An alert is emailed only when `notification_email_enabled` is also on. `digest_email_enabled` (default `false`) sends at most one email a week, "Your week on Illini SkillShare", listing requests that need your action and new teachers of your goals. Nothing is sent in a quiet week, and a failed send is not retried that week. Both flags are writable on `/api/profiles/me/` and included in the account export.

GET `/api/discovery/community/` (signed in) returns cold-start hints: `{member_count, popular: [{id, name, teachers}] (up to 8), unmet: [{id, name, learners}] (up to 5 skills that members with public learning goals want and no discoverable member teaches), my_untaught_goals: [{id, name}] (your own goals nobody teaches)}`. Counts use the same visibility rules as discovery. Learner counts only include members who made their learning goals public. The dashboard also returns `attention_items` (up to 10 `{action, request_id, href, kind, topic, skill, peer: {name, profile_id}, updated_at}` where `href` is `/requests/<id>` and `action` is `respond` for incoming pending requests, `complete` for accepted ones and `feedback` for completed requests you have not reviewed yet (the seeker, or either side of a swap); requests with hidden or blocked peers are omitted) and `checklist` (`{key, label, done, href}` for publish, bio, second_skill, contacts, avatar and evidence). Network administration is staff-only at `/api/admin/analytics/summary/`.

For staff, `/api/analytics/summary/` also returns `launch_metrics`: `{signups, setup_completion_rate, median_minutes_to_first_match, sent_request_within_7_days_rate, sent_request_cohort, acceptance_rate, median_response_hours, completion_rate, feedback_rate, two_sided_swap_feedback_rate, review_count, generated_at}`. Rates are fractions from 0 to 1, and medians are `null` when there isn't enough data. Signups count verified, non-demo, non-staff members. Time to first match runs from account creation to the first `matches_shown` event, which is recorded the first time search, swap matches or recommendations return at least one profile. The 7-day request rate only counts members who finished setup at least seven days ago. Acceptance is accepted ÷ (accepted, declined or expired). Completion is completed ÷ ever accepted. Feedback is completed requests with at least one review. Two-sided feedback is completed swaps reviewed by both people.

## Launch, SEO and error reporting

POST `/api/client-errors/` takes `{message, source?, path?, release?}` with no session or CSRF and always returns 204. It is throttled to 30 per hour per IP. The server strips emails, long tokens and digit runs, replaces numeric path segments with `:id`, and groups repeats by fingerprint (`count`, `first_seen`, `last_seen`), which staff can view read-only in the Django admin. `CLIENT_ERROR_REPORTING=false` turns storage off. The browser sends at most 10 distinct reports per page load, ignores failed API calls (they already have error states), and stays silent when `VITE_ERROR_REPORTING=false`.

`/robots.txt` allows the landing, sign-in and policy pages and disallows the API, admin and signed-in screens. `/sitemap.xml` lists those public pages. Every other HTML route is served with `X-Robots-Tag: noindex`. The SPA shell fills its canonical, Open Graph and Twitter URLs from `APP_PUBLIC_URL`. Each screen sets `document.title` to "<Screen> · Illini SkillShare".

Health endpoints are unauthenticated: `/api/health/live/` (process) and `/api/health/ready/` (PostgreSQL and Redis). Provider outages return truthful fallback/error states; email failures do not roll back requests.
